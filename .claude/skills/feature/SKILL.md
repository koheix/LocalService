# 機能を 1 本の PR として仕上げる

引数で受け取った内容（`$ARGUMENTS`）を、llm-console の規約に沿って実装し PR にする。
**途中の工程を飛ばさない。** 特にテスト設計と監査は、飛ばすと後で必ず高くつく。

対象が `docs/TASKS.md` の未完了タスクに対応する場合は、`/next-task` の手順
（完了条件の読み上げと合意）を先に行ってから、この先の工程に進む。

## 0. 前提を確かめる

`git status` で現在地を確認する。未コミットの変更があるなら、それを先に片付けるか
別ブランチに退避するかをユーザーに確認する。

## 1. origin と同期してブランチを切る

```powershell
git fetch origin --prune
git switch main
git pull --ff-only
git switch -c feature/<内容がわかる名前>
```

ブランチ名の接頭辞は `feature/` `fix/` `chore/` `refactor/` から選ぶ。

> `origin/main` から切ること。前の作業ブランチから枝分かれさせない。

## 2. 対象を読む

実装に入る前に、変更する範囲のコードを読む。既にある関数や書き方を使えるなら、
新しく作らない。設計上の決めごとは `CLAUDE.md`、`docs/ARCHITECTURE.md`、
`docs/API.md`、`docs/SCHEMA.md` を参照。仕様に書かれていない判断（特に認証・権限・
VRAM配分）が必要なら、ここで止まってユーザーに聞く。

## 3. テストを設計させる

`test-designer` エージェントに、これから実装する内容と読んだファイルを渡して
テスト仕様を作らせる。

返ってきた「落とし穴」と「テストしやすさの問題」を読み、
**必要なら実装方針のほうを変える**（判断ロジックを注入可能にする、
`InferenceBackend` の抽象に依存する形にする、など）。

## 4. 実装する

- **バックエンド固有の処理（Ollama の語彙）は `app/backends/` に閉じ込める。**
  ルーター層は `InferenceBackend` 型しか知らないようにする
- DBアクセスは必ず async。同期ドライバを混ぜない
- 例外は `app/errors.py` の独自例外に集約し、exception handler で JSON 化する
- 推論ログ（`usage_logs`）の記録は best-effort にする。記録に失敗しても
  推論レスポンスは正常に返す（例外を握って warn ログにする）
- prompt 本文をログに含めない（`ENABLE_PROMPT_LOGGING=false` が既定）
- 認証はセッションCookieとAPIキーの両方に対応させ、Argon2id でハッシュ化する

## 5. テストを書く

3 で設計した項目を実装する。テスト関数名は簡潔な英語の snake_case にし、
1行目の docstring で「何を保証するのか」を日本語で書く。

```python
def test_rate_limit_returns_429_with_retry_after():
    """レート制限の上限に達したら 429 を Retry-After ヘッダ付きで返す。"""
    ...
```

- テストは `gateway/tests/` に、`app/` の構成をなぞって置く
- Ollama バックエンド・時計・乱数はフェイクに差し替える。DBが絡む統合テストは
  実 PostgreSQL（pgvector 入り、`docker compose` の `postgres` サービス）に対して行う
- 実バックエンド（Ollama）を実際に叩くテストは既定で実行しない。手動確認用に
  環境変数でゲートする
- 期待値は実装と同じ式で計算せず、定数でベタ書きする

## 6. テストを監査させる

`test-auditor` エージェントに、書いたテストと対象の実装を渡す。

**不合格なら直す。** 「指摘は受けたが今回はこのまま」は無し。
監査を通せないテストは、壊れたときに落ちない。

## 7. テストを実行する

`test-runner` エージェントに実行させる。

落ちたら原因を直す。**テストを緩めて通してはいけない。**
全部緑になるまで 6 と 7 を繰り返す。

## 8. コミットする

意味のある単位で分ける。1 コミット 1 目的。

```powershell
git add <対象>
git commit
```

コミットメッセージは日本語。1 行目に何をしたか、本文になぜそうしたかを書く。

## 9. セルフレビューする

`pr-reviewer` エージェントに `origin/main...HEAD` の差分を見せる。
指摘があれば直してから次へ。

## 10. PR を作る

`/ship-pr` スキルを使う。テスト結果が本文に埋め込まれた PR ができる。

## 11. 報告する

ユーザーに次を伝える。

- PR の URL
- 何を実装したか
- テスト結果（成功／失敗の件数）
- レビューで特に見てほしい箇所
- 意図的にやらなかったこと

## 守ること

- **工程を飛ばさない。** 急かされても、テスト監査だけは飛ばさない
- 途中で判断に迷ったら、勝手に決めずにユーザーに聞く
- PR はマージしない。マージは人間がやる
