# 本番／検証機へ反映する

**このスキルは既にマージされた `main` の内容をホストに反映するためのもの。**
未マージの変更を勝手にデプロイしない。

llm-console は Phase 0 では**社内に1台設置した実機**上で `docker compose` として動く
（クラウドの管理コンソールへのデプロイではない）。GPU を占有するサービスの再起動を伴うため、
実行前に必ずユーザーに「何を（対象コミット）」「いつ（利用者への影響）」反映するかを確認する。

## 1. 対象を確認する

```powershell
git status --short --branch
git log --oneline -5
```

`main` の最新であることを確認する。作業ブランチのままデプロイしようとしていないか確認する。

## 2. テストを実行する

```powershell
make test-report
```

**1 つでも失敗しているなら、デプロイを止めて報告する。** ユーザーが明示的に
「テストが落ちていてもデプロイして」と言わない限り進めない。

## 3. マイグレーションの内容を確認する

**マイグレーションはコードの反映より先に、かつ慎重に適用する。**
破壊的な変更（列の削除・型変更・既存行を壊しうる NOT NULL 化）が含まれていないか、
`gateway/alembic/versions/` の差分を確認する。含まれているならユーザーに内容を説明し、
承認を得てから進める。

```powershell
git diff origin/main~<N>..origin/main -- gateway/alembic/versions
```

## 4. ホスト上で反映する

**この手順は実機（社内設置の GPU サーバー）上で実行する想定。** 手元の開発機から
リモートに push するだけの操作ではない。実機での実行をユーザーに依頼するか、
リモート実行が可能な場合はその方法を確認する。

```bash
git pull --ff-only
make migrate
make up            # --build で新しいイメージに切り替わる（短時間の再起動を伴う）
```

同時利用者は1名という前提だが、再起動中はその1名も使えなくなる。**タイミングを確認する。**

## 5. 動作を確認する

反映して終わりにしない。最低限これを確認する。

```bash
make smoke
```

- `curl http://<ホスト>/api/health` が `200` を返す
- ログイン→推論→`usage_logs` への記録が通ることを確認する
- GPU 側の状態（`/vram` スキル、または `nvidia-smi`）で VRAM 使用量が想定内であることを確認する

## 6. 報告する

- 反映したコミット
- 適用したマイグレーション（あれば）
- 確認した内容
- 問題があったときの切り戻し手順
  （直前のコミットへ `git checkout` して `make up` を再実行、
  マイグレーションは `alembic downgrade` が必要な場合はその手順も添える）

## 守ること

- テストが通っていない状態でデプロイしない
- マイグレーションは事前にユーザーと内容を確認する（特に既存データに影響するもの）
- **`docker-compose.yml` を編集して `ollama` / `ollama-embed` のポートを
  ホストに公開する変更を混ぜない**
- 本番機（Phase 3、vLLM 対応後）への切り替えでは、GPU の compute capability が
  vLLM の要件（7.0 以上）を満たすかを事前に確認する
