# GitHub Issue を 1 本の PR に仕上げる

引数（`$ARGUMENTS`）で受け取った Issue 番号または URL を起点に、llm-console の規約に沿って
実装し PR にする。**工程を飛ばさない。**

このSkillは `feature` スキルの Issue 版にあたる。違いは次の2点。

- 出発点が「ユーザーの口頭指示」ではなく **Issue に書かれた要望**であること
- 完了条件が **Issue の受け入れ条件**で決まること

## 0. Issue を取得する

```powershell
gh issue view <番号> --json number,title,body,labels,state,url,comments
```

コメント欄に補足や仕様変更が書かれていることがあるので、**本文だけで判断しない**。

Issue が `closed` なら、なぜ着手するのかをユーザーに確認してから進む。

## 1. Issue を理解する

次を自分の言葉で整理する。**Issue に書かれていないことを補わない。**

| 項目 | 内容 |
|---|---|
| 要望 | 何を実現したいのか |
| 背景 | なぜ必要なのか |
| 受け入れ条件 | 何が満たされれば完了か |
| 制約 | やってはいけないこと、触ってはいけない範囲 |

**受け入れ条件が書かれていない場合**は、調査のあとに自分で草案を作り、
「この理解で合っているか」をユーザーに確認してから実装に入る。勝手に決めない。

仕様上の重要な不明点があり、合理的に判断できないなら **そこで止まってユーザーに聞く**。
推測で実装しない。**特に認証・権限・VRAM配分に関わる判断は、CLAUDE.md が明示的に
勝手な決定を禁じている。**

## 2. 現在地を確かめてブランチを切る

```powershell
git status
git fetch origin --prune
git switch main
git pull --ff-only
git switch -c feature/issue-<番号>-<内容がわかる名前>
```

接頭辞は内容に応じて `feature/` `fix/` `chore/` `refactor/` から選ぶ。
`origin/main` から切る。前の作業ブランチから枝分かれさせない。

未コミットの変更があるなら、先に片付けるか退避するかをユーザーに確認する。

## 3. リポジトリを調査する

実装に入る前に読む。**ここを飛ばすと既存の仕組みを二重に作る。**

- `CLAUDE.md`（守るべき規約）と `docs/ARCHITECTURE.md`（設計の正本）
- `docs/API.md`（エンドポイント仕様）、`docs/SCHEMA.md`（DBスキーマ）
- `docs/DECISIONS.md`（過去に踏んだ落とし穴・却下した代案）
- Issue が触れている機能の実装（`gateway/app/`）とテスト（`gateway/tests/`）
- 似たことを既にやっている箇所（同じ書き方を使えるなら新しく作らない）

調査結果から次を整理し、ユーザーに短く共有する。

- 変更対象と、その理由
- 実装方針
- テスト方針
- リスクと、影響が及ぶ範囲

## 4. テストを設計させる

`test-designer` エージェントに、Issue の受け入れ条件と読んだファイルを渡してテスト仕様を作らせる。

返ってきた「落とし穴」と「テストしやすさの問題」を読み、
**必要なら実装方針のほうを変える**（判断ロジックを注入可能にする、
`InferenceBackend` の抽象に依存する形にする、など）。

## 5. 実装する

- **バックエンド固有の処理（Ollama の語彙）は `app/backends/` に閉じ込める。**
  ルーター層は `InferenceBackend` 型しか知らないようにする
- DBアクセスは必ず async。同期ドライバを混ぜない
- 推論ログ（`usage_logs`）の記録は best-effort にする。記録に失敗しても推論レスポンスは壊さない
- 認証はセッションCookieとAPIキーの両方に対応させ、Argon2id でハッシュ化する
- **Issue に書かれていない大規模なリファクタリングをしない。** 必要以上に既存コードを変えない

## 6. テストを書く

テスト関数名は簡潔な英語の snake_case にし、1行目の docstring で「何を保証するのか」を
日本語で書く。

- `gateway/tests/` に `app/` の構成をなぞって置く
- Ollama バックエンド・時計・乱数はフェイクに差し替える。DBが絡む統合テストは
  実 PostgreSQL（pgvector 入り、`docker compose` の `postgres` サービス）に対して行う
- 期待値は実装と同じ式で計算せず、定数でベタ書きする

**受け入れ条件のひとつひとつに、対応するテストがあるようにする。**

## 7. テストを監査させる

`test-auditor` エージェントに、書いたテストと対象の実装を渡す。**自分で書いたテストを
自分で監査しない。** 実装した本人が見ると、通っていることを確認するだけになる。

不合格なら直す。「指摘は受けたが今回はこのまま」は無し。

## 8. テストを実行する

`test-runner` エージェントに実行させる。

```powershell
make test-report
make fmt
```

落ちたら原因を直す。**テストを緩めて通してはいけない。テストを消して通してはいけない。**
全部緑になるまで 7 と 8 を繰り返す。

## 9. 受け入れ条件を1つずつ確認する

Issue に書かれた受け入れ条件を順に見て、**満たしている根拠**（どのテスト、どの動作確認）を
書き出す。満たせていないものがあるなら、実装に戻るか、なぜ満たさないのかを PR に書く。

あわせて次も確認する。

- 不要な変更が混ざっていない
- デバッグ用のコードやログが残っていない
- 秘密情報（`SECRET_KEY`、`POSTGRES_PASSWORD`、`ADMIN_INITIAL_PASSWORD`、
  APIキーの平文）をコミットしていない

## 10. コミットする

意味のある単位で分ける。1 コミット 1 目的。メッセージは日本語で、
1 行目に何をしたか、本文になぜそうしたかを書く。

## 11. レビューさせて、記録する

`pr-reviewer` エージェントに `origin/main...HEAD` の差分を見せる。指摘があれば直す。
直したらテストを実行し直す（記録はコミットに紐づくので、直したあとの記録が要る）。

レビューが済んだら記録する。この記録が無いと次の工程（PR 作成）に進めない。

```powershell
python scripts/record_review.py --reviewers test-auditor,pr-reviewer --verdict pass
```

指摘が残っているなら `--verdict changes-requested` で記録し、直してから記録し直す。

## 12. PR を作る

`/ship-pr` スキルを使う。そのうえで、**PR 本文に Issue との紐付けを必ず書く。**

```
Closes #<番号>
```

PR 本文には次を含める。

- 変更概要と、そうした理由
- Issue の受け入れ条件それぞれの達成状況
- テスト結果（成功／失敗の件数）
- 意図的にやらなかったこと

## 13. 報告する

ユーザーに次を伝える。

- PR の URL と、対応する Issue 番号
- 受け入れ条件を満たせたか（満たせていないものがあれば、その理由）
- テスト結果
- レビューで特に見てほしい箇所
- 判断に迷って自分で決めたところ

## 守ること

- **Issue に書かれていない実装方法を勝手に決めつけない**
- 不明点は推測せず、止まって聞く（特に認証・権限・VRAM配分）
- テストを削除・弱体化して通さない
- **PR を作ったらそこで止まる。** マージ・承認・デプロイへ進まない
- PR はマージしない。マージは人間がやる
- Issue を勝手にクローズしない。`Closes #N` を書いた PR がマージされれば自動で閉じる

最後の3つは `.claude/hooks/guard-gh.ps1` が機械的に止める。止められたら迂回せず、
利用者に PR の URL を伝えて終わる。
